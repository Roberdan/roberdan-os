## Novelties + impact

### 1. Copilot CLI — `defaultMode` and `defaultPermissionMode` settings

**Evidence.** Weekly releases — August 24, § GitHub Copilot CLI: "Start every new session with your
preferred execution and permission modes using `defaultMode` and `defaultPermissionMode`."

**Impact on roberdan-os — this is the item worth Roberto's attention.** On this machine the permission
mode is set today by a shell alias, not by configuration:

```
$ zsh -ic 'type copilot'
copilot is an alias for gh copilot --yolo          # ~/.zshrc:137
```

The flag reaches Copilot and does what it says — verified empirically on 2026-08-29, not inferred
(`gh copilot --help` warns that flags for Copilot need a `--` separator, and this alias has none, so it
had to be tested):

```
$ gh copilot     -p 'run the shell command: echo YOLOTEST'   → exits without running it (approval needed)
$ gh copilot --yolo -p 'run the shell command: echo YOLOTEST' → runs it, prints YOLOTEST, exit 0
```

`--yolo` auto-approves every tool call, for every repo, invisibly — it does not appear in
`~/.copilot/settings.json`, is not generated or checked by `bin/sync.sh`, and `bin/doctor.sh:136` only
verifies the binary exists. The canon's control on this class is blast radius, not prose
(`rules/best-practices.md` § *Security & Privacy*: "least-privilege tools … secrets physically
unreachable from where generated code runs"), and `~/.copilot/permissions-config.json` already stores
per-location tool approvals that a blanket `--yolo` renders moot.

`defaultPermissionMode` moves that decision into a file that can be read, reviewed, diffed and checked
by `doctor.sh` — which is the whole point.

**State of the installed CLI — what was actually observed.** No evidence the keys work on 1.0.82-1:
neither name appears in the installed binary's strings
(`grep -ac defaultPermissionMode ~/.local/share/gh/copilot/copilot` → **0**, same for `defaultMode`),
neither appears in `~/.copilot/settings.json`, and the announcement postdates the installed version.
A strings grep on a packed binary is suggestive, not proof — a key name can be built at runtime. Either
way the patch needs `copilot update` first, then confirmation of the accepted values against the updated
CLI.

**Suggested patch, awaiting Roberto (two steps, the first is his call).**

1. Decide whether the default stays `--yolo`. If yes, say so once in the canon so it is a recorded
   decision rather than an alias nobody re-reads; if no, set a narrower default.
2. After `copilot update`, express it as configuration instead of an alias:

```diff
--- ~/.copilot/settings.json
+  "defaultPermissionMode": "<value confirmed against the updated CLI>",
+  "defaultMode": "<value confirmed against the updated CLI>",
```

```diff
--- a/~/.zshrc:137
-alias copilot='gh copilot --yolo'
+alias copilot='gh copilot'
```

plus a read-only line in `bin/doctor.sh` next to the existing `~/.copilot/mcp-config.json` check
(`bin/doctor.sh:186`) that WARNs when the effective permission mode is the permissive one — the same
check-don't-write pattern that file already uses. Citation: weekly releases — August 24 (pubDate
2026-08-28).

### 2. Copilot CLI — restoring sessions that did not exit cleanly, including mid-turn

**Evidence.** Same entry: "Pick up where you left off by restoring sessions that did not exit cleanly,
including sessions interrupted mid-turn."

**Impact on roberdan-os.** This is host-native support for what the `long-running-jobs` skill states as
discipline: durable state, terminal-condition, **resume-not-redo**. It does not replace the discipline —
the durable ledger is still `kb` and the handoff, and a restored session is not evidence that the work
finished (`rules/best-practices.md` § *No False Done*). What it changes is that a Copilot session killed
mid-card can now be resumed rather than restarted from the card, which is worth one sentence in the skill
so an agent knows to try resume before redo.

**Where the skill actually lives — checked.** `long-running-jobs` is **not** in this repo:
`ls skills/` returns `auto-checkpoint engineering-reference focus-group model-selection-policy premortem
problem-validation review ship sync verify-done`. The live file is
`~/.claude/skills/long-running-jobs/SKILL.md` (also present under `~/.agents/` and `~/.junie/`), so it is
outside the canon and outside `bin/sync.sh`'s generation. Patching it is a machine edit, not a repo commit.

**Suggested patch, awaiting Roberto.** One line under resume in `~/.claude/skills/long-running-jobs/SKILL.md`:
Copilot CLI (≥ the version shipping this change, to be confirmed after `copilot update`) restores
uncleanly-exited sessions, so *resume the session first, re-read the card second*. Doc only, no behaviour
change. Separately worth deciding: whether that skill should move into `skills/` so it is versioned with
the rest — three unsynchronised copies exist today. Citation: weekly releases — August 24 (pubDate 2026-08-28).

### 3. Copilot CLI — native Rust runtime

**Evidence.** Same entry: "Get significantly faster performance now that Copilot CLI runs on a native
Rust runtime, while its terminal interface remains built in TypeScript."

**Impact on roberdan-os.** A runtime swap under a CLI that this repo installs into
(`~/.copilot/skills`, `~/.copilot/agents`, `~/.copilot/extensions/roberdan-os/extension.mjs` —
`bin/sync.sh:37-56`) is exactly where a silent breakage would land, and the extension is a `.mjs` module
loaded by the host. Nothing observed broken: the extension and skills are installed and the CLI runs at
1.0.82-1 today, but that version predates the change, so the real check happens after `copilot update`.

**Suggested patch.** None now. Action: after the next `copilot update`, run `bin/sync.sh --install` and
`bin/doctor.sh`, and confirm the roberdan-os extension still loads. Recorded here so it is not
rediscovered as a mystery failure.

### 4. Copilot CLI — new `/plugin`, `/mcp`, `/skills` experiences

**Evidence.** Same entry: "Manage plugins, MCP servers, and skills more easily with new experiences in
`/plugin`, `/mcp`, and `/skills`."

**Impact on roberdan-os.** Interactive management surfaces over directories this repo writes by symlink
(`bin/sync.sh:37-56`, `bin/lib-skills-install.sh`). The risk is not the feature but the direction of
travel: if a `/skills` UI can disable or remove an entry, the live state can drift from what `sync.sh`
generated, and `~/.copilot/skills-disabled` already exists on this machine. That drift is invisible to
`git status` — the canon's own "built ≠ active" trap. **No patch proposed**; flagged as the one item in
this batch worth a follow-up card if drift is ever observed.
